## Findings

### AR-1 — Call 3's fields cannot tell an open issue from an open pull request

**Where:** F-07, Contract → The command → GitHub, call 3, lines 151–153; A blocker's status, lines 179–183; the page,
lines 205–206. Also F-17, §5 call 2, `dev/features/parallel-plan.md` lines 366–368.

Call 3 asks `issueOrPullRequest(number: n)` with `... on Issue { state stateReason }` and `... on PullRequest {
state }`, and no `__typename`. The page then has to print "(open)" for an issue but "(pull request, open)" for a pull
request, and link the second to `/pull/{n}`. GitHub's answers, asked on 2026-11-04, are `{"state":"OPEN"}` for an
open pull request and `{"state":"OPEN","stateReason":null}` for an open issue. Only the presence of a key that is
`null` tells them apart. Closed is the same: `CLOSED` on both, `stateReason` present on one.

Two easy implementations go wrong. Reusing `statusOf()` (`ci/work-order.mjs:77`) on the answer reads `MERGED` as
`open`, since it tests only `CLOSED`, so a merged pull request holds its leaf for good: #607's own symptom, back. And
the test stub builds every answer from `issue()` (`scripts/work-order.test.mjs:40`), which sets `stateReason: null`,
so a fixture for a pull request built the usual way reads as an issue. Nothing in the Contract or Acceptance would
catch either. #607's own reproduction asked `__typename`; the Contract dropped it.

**Proposed resolution.** Add `__typename` to call 3's selection in F-07 and to F-17 §5 call 2, and say that the kind
(issue or pull request) is read from it, never from which keys are present. Acceptance block 1 or 2 can then say the
stub answers the pull request with `__typename: "PullRequest"`.

### AR-2 — "the same as in a run where no ticket names that number" cannot hold for picks

**Where:** F-07, Acceptance, the third block under "Blocked by numbers that are not issues (#607)", lines 344–349; the
rule it tests, A blocker's status, lines 183–185. Also F-17, Acceptance, `dev/features/parallel-plan.md` lines
685–689.

The block says the leaf with the unknown blocker "is not in Next, and every other leaf, blocker and pick is the same
as in a run where no ticket names that number". In that comparison run the leaf has no unknown blocker, so it can be
ready. When it is, it is picked: it takes one of the three places, and its `Touches:` keeps any overlapping leaf out
of Next. The other picks then differ, and a correct build fails the test. The criterion passes only when the fixture
happens to make the leaf unpickable for some other reason. F-17's block has the same comparison: "every other GitHub
line is the one a run with no ticket naming that number prints", and in that run the leaf is offered.

**Proposed resolution.** Compare against a run where that number is answered as an open issue. That run holds the
leaf in the same way, so every other leaf, blocker and pick, and in F-17 every other line, must match. The Contract's
"every other leaf and blocker reads as it would without that number" (184) can say the same.

### AR-3 — F-07 and F-17 disagree on a `NOT_FOUND` for a milestone item's issue

**Where:** F-07, A blocker's status, lines 184–185 ("An answer with a `NOT_FOUND` error beside any other error still
fails the run"); the second `Verified against:`, lines 96–97 (`realGh()` keeps an answer whose every error is
`NOT_FOUND`); Leaves, line 166 (not amended). Also F-17 §5, `dev/features/parallel-plan.md` lines 325–327, and §10,
552–554.

F-07 keeps any answer whose errors are all `NOT_FOUND`, on any call (`ci/work-order.mjs:53`). A started item whose
marker names a pull request, a typo or a deleted issue shows "#n not found", and the page goes on. F-17 0.4 says
the opposite for status: "A `NOT_FOUND` beside any other error, or on another call's alias, fails the read". Call 1
folds in work-order's item read, so one milestone marker naming a deleted issue or a pull request gives status no
GitHub data, in every session. That is the outcome #607's Observed warns of ("one ticket that names a pull request
could leave status with no GitHub data, in every session"), moved from the blocker caller (`:131`) to the item
caller (`:108`). #607's Root cause names both callers. F-17 §10 then has the page read through the same calls with
"the same rule", so at F-17's step 5, F-07's line 166 stops being true without either doc saying so.

**Proposed resolution.** Pick one rule for an item's issue that GitHub does not return, and write it in both docs.
One option: F-17 treats a call-1 item alias answered `null` with `NOT_FOUND` as F-07 does (the item shows "#n not
found", plus a Needs attention line), and fails the read only for any other error. This is the owner's call, since
D-050's all-or-nothing rule is the owner's (Q3).

### AR-4 — The page offers `/work-ticket` on a ticket `/work-ticket` would stop on

**Where:** F-07, Contract → GitHub, call 3, lines 152–153 ("A `Blocked by:` line may name a pull request on purpose,
to hold a ticket until it merges"); Ready, lines 186–187; the page, line 207 (the `/work-ticket {n}` command).

0.2 makes a pull request number on a `Blocked by:` line a supported form, and once that pull request merges the page
offers the ticket with `/work-ticket {n}`. `/work-ticket` step 3 (`.claude/skills/work-ticket/SKILL.md:67`) says:
"Every `Blocked by:` or `Depends on:` issue (`#` and digits) is closed. One is open: stop." `gh issue view` on a merged
pull request gives `MERGED` (#607, Other readers), not closed, so a literal reading stops. `process/intake.md:114`
documents `Blocked by: #n`, and `:17` says an issue reference is `#` and digits; neither says a pull request number is
allowed. #607's Root cause names this, and its Acceptance does not cover it. So the page and the skill it hands the
owner to would read the same line two ways.

**Proposed resolution.** #607's fix, or a follow-up it names, has `/work-ticket` step 3 read a merged pull request, or
one closed without merging, as cleared, the way F-07 0.2 reads it. `process/intake.md`'s Links rule says a
`Blocked by:` number may be a pull request. Both files are owner-only, so this needs the owner's yes. F-07's Contract
can name where that rule lives.

### AR-5 — "a deleted or moved issue" is said to answer like a typo, without a reproduction

**Where:** F-07, A blocker's status, lines 181–182 ("its alias `null`, beside an error of type `NOT_FOUND`: a typo, a
deleted or moved issue"); the second `Verified against:`, lines 99–100.

The `Verified against:` line records three answers: a merged pull request, an issue, and "a number it holds as
neither". That last one is a typo-like number. #607 says of a deleted or moved issue: "Not reproduced here: no
deleted or moved issue was at hand to ask about." The Contract states the case as fact. If GitHub answers a
transferred issue in some other way, for example with a different error type, the 0.2 rule fails the whole run for
it, which is the behaviour 0.2 exists to remove.

**Proposed resolution.** Either ask GitHub about a transferred issue and record the answer on the `Verified against:`
line, or narrow line 182 to "a number nothing holds". Then add one Known limitations line: an answer of any other
shape fails the run, as before.

### AR-6 — The unknown-blocker finding shows on leaves it does not hold

**Where:** F-07, A blocker's status, lines 182–183 ("its leaf carries one finding"); the page, line 207. Also F-17 §5
call 2, lines 372–374 ("one `blocker-unknown` line per leaf and number … It blocks #{m} being offered").

Blockers are read for every leaf, whatever its status (`ci/work-order.mjs:136`–`137`). So a done or dropped leaf
whose closed issue still names a typo gets the finding "Correct the number or remove it", which asks the owner to
edit a closed issue. That finding sits inside the folded "done or dropped" `<details>`. A leaf already in progress
gets it too. In F-17, the line says "It blocks #{m} being offered", which is false for a leaf that is closed or already
has a pull request.

**Proposed resolution.** Show the finding, and print F-17's line, only for a leaf whose status is `open`, the only
status a blocker holds back from Next. Say so in both docs.

### AR-7 — Acceptance blocks 1 and 2 are worded so they can pass when wrong

**Where:** F-07, Acceptance, the first and second blocks under "Blocked by numbers that are not issues (#607)", lines
330–341.

Block 1 says "Given a ready leaf whose Blocked by: names an open pull request". By the Contract's own Ready (186–187)
that leaf is not ready, so the Given contradicts the Then it sets up. Block 2's Then is "the leaf is in Next when
nothing else holds it". When the leaf is missing from Next, a test can always point to something else holding it,
so the criterion cannot fail.

**Proposed resolution.** Block 1: "Given an open leaf with no other hold, whose Blocked by: names an open pull
request". Block 2: move "nothing else holds the leaf" into the Given, and make the Then "the leaf is in Next".

### AR-8 — "Ready", as 0.2 rewrites it, leaves out F-09's hold

**Where:** F-07, Contract → The model → Ready, lines 186–187.

0.2 restates Ready as "status `open`, and every blocker cleared". The code also holds a leaf that owes a check
(`ci/work-order.mjs:138`, `!l.owes`), the hold F-09 added (`dev/features/deferred-checks.md:261`). The Fit names
`owing()` as reused, so this doc already relies on it. "An issue closed (either reason)" speaks of two reasons; GitHub
has three close reasons (completed, not planned, duplicate), and Leaf status (167) names all three.

**Proposed resolution.** "Ready: status `open`, the item owes no check (F-09), and every blocker cleared: an issue
closed for any reason, or a pull request merged or closed without merging."

### AR-9 — The finding's text puts the action last, and differs from F-17's for the same fact

**Where:** F-07, A blocker's status, lines 182–183. Also F-17 §5 call 2, lines 373–374.

F-07: "#{m} names #{n} on its Blocked by line, which is neither an issue nor a pull request in {repo}. Correct the
number or remove it." `process/writing.md` rule 1 puts the action first. F-17's line for the same fact does:
"Correct #{n} on #{m}'s Blocked by line, or remove it. It is neither an issue nor a pull request in this repository."
The owner will see both texts for one ticket, and F-17 §10 already plans for the page and status to share their
reading.

**Proposed resolution.** F-07 uses F-17's first two sentences, with `{repo}` in place of "this repository" if the
page wants it. F-17's who, blocks and waits tail stays status's own.

### AR-11 — F-17 §10 still says F-07 has no `## Fit`

F-17 §10 says "F-07 has no `## Fit`, so `/review-doc` cannot review it", and has step 5's ticket carry an Acceptance

### AR-12 — A pull request closed without merging frees its ticket early

**Where:** F-07, Ready, lines 186–187; call 3, line 153 ("to hold a ticket until it merges"). Also F-17 §5 call 2,
lines 369–370.

The stated purpose of a pull request on a `Blocked by:` line is to hold a ticket until that pull request merges. A
pull request closed without merging clears the hold. When a pull request is closed and replaced by a new one, the
ticket is offered before the work it waits for has landed. #607 records this as the owner's choice of 2026-11-02 ("closed
without merging clears the way a dropped issue does"), so this finding argues nothing against it beyond the case
above.

**Proposed resolution.** Keep the owner's rule, and add one Known limitations line: a pull request closed to be
replaced frees its tickets; name the new pull request on the `Blocked by:` line.
